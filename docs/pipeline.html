Canonical mission flow

The ten documented routing stages are shown in execution order. Component labels describe the primary responsibility, not an exclusive implementation boundary.

01
RVIA
Mission intake

Accept the governed mission envelope and establish the routing contract for the requested work.

02
IDENTITY
Scope + principal

Resolve who or what is acting, the allowed scope, and the authority attached to the mission.

03
SHADOW GLASS
Preflight

Inspect mission context and constraints before planning or external action is allowed to proceed.

04
ONTOLOGY CONTEXT
NXYZ + knowledge graph

Ground objects, links, repositories, services, evidence, policies, and prior state in the shared ontology.

05
PLANNER
Reasoning layer

Turn the grounded mission into an explicit plan with required capabilities, bounded tools, and verification criteria.

06
ZYRA AUTHORIZATION
Policy gate

Authorize, deny, or require approval based on policy, mutation risk, scope, and the requested tool boundary.

07
DISPATCH
XUNIA orchestration

Route approved work to the registered builder, agent, cloud, registry, or integration target needed for the mission.

08
GLASS ONION
Verification

Compare claimed outcomes with observable results, tests, postconditions, and returned tool evidence.

09
EVIDENCE
Proof capture

Persist result evidence, provenance, attempts, outputs, and verification state instead of relying on completion claims.

10
AUDIT
History + feedback

Record the durable mission timeline and feed verified state back into later routing and ontology context.

DENY / HOLD PATH

If Zyra authorization fails or required approval is missing, dispatch does not proceed. The denial/hold state and reason become part of the mission record.

VERIFY → REPAIR → RETEST LOOP

A failed verification result can return the bounded mission to planning or execution for repair. Success is based on observed proof, not an agent saying “done.”

CONTROL PLANE

The Black House defines the canonical mission, routing, ontology, agent/service registry, evidence, and audit contracts.

EXECUTION BOUNDARY

XUNIA coordinates approved work. External writes and higher-impact mutations remain subject to authorization and postcondition checks.
